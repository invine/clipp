# Reviewed evidence applicability: ledger v3

V3 can retain an original observation across a new integration candidate through an explicit, separate carry-forward. V1/v2 retain their exact-current-tip rule. V3 without applicable carry-forward records also requires current-tip evidence. Neither a carry-forward nor a consistent scenario allocation is a new execution, scenario qualification or permission.

The coordinator records these optional collections in [run schema v3](run-v3.schema.json):

| Collection         | Required binding                                                                                                                                                           |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `candidates`       | Unique `id`, exact per-role `revisions`, and `inputs` with SHA-256 fingerprints for `toolchain`, `dependencies`, `build`, `runner`, `fault`, `artifact` and `environment`. |
| `evidenceBindings` | Original `evidenceId`, original `candidateId`, complete owned `scenarioIds`, `scenarioDigest`, and public `relevantInputs` as `{role, path}` references.                   |
| `carryForwards`    | Original `evidenceId`, one `scenarioId`, new `candidateId`, unchanged `relevantInputs`, complete `assessedChanges`, explicit `rationale` and `reviewer`.                   |

The original candidate's revision map must equal the observation's revision map. Preserve the original evidence's result, date, tools, reviewer and revisions. The new candidate must match the current integration revision for every original role. Each candidate input fingerprint identifies the measured input or preserved receipt, including concrete versions/configuration, rather than an assumed default. Missing/unknown inputs require review or rerun; do not manufacture equal fingerprints. The candidate-preparation command's bound manifest supplies source/toolchain/dependency/build/artifact provenance; explicit runner, fault and environment records supply the remaining context. Fingerprints are coordinator attestations to that provenance: status checks their presence and equality, without opening private artifacts or certifying their contents.

`scenarioDigest` is the SHA-256 of UTF-8 `JSON.stringify` of the original complete owned scenario objects, in allocation order. For example, compute it from `ledger.scenarios.filter(item => item.primaryOwner === evidence.ticket)`. Preserve the original allocation ordering and object representation when recording it. A different allocation, missing scenario, observation expectation, evidence boundary or runtime requires renewed evidence; changing the current digest to conceal a changed contract is not a valid migration.

`relevantInputs` names the source files or directories the reviewer assessed as relevant to the scenario. Include all relevant runtime/bridge inputs across the observation's roles. Those objects must remain available and unchanged. Requirement sources and the public specification are automatically protected even if omitted from this list. Adding an incomplete list does not establish dependency coverage: the coordinator and semantic Spec reviewer own that assessment. The command does not certify a universal dependency graph.

Each `assessedChanges` item has `role`, public `path`, actual Git object IDs `before` and `after` (or `absent` for an added/deleted path), `assessment` and a concrete `rationale`. Obtain object IDs with `git rev-parse --verify <revision>:<path>` at the original and new revisions. The command independently derives the complete committed change set, with renames treated as deletion plus addition, and checks those object IDs. A copied assessment for a different edit fails even when its filename is unchanged. No source diff text, external diff driver, recorded command or private artifact content is read or executed. The narrow canonical-issue exception below reads only bounded historical public ticket blobs.

Assessment values are `status-only`, `documentation-only`, `unrelated`, `changed` or `unknown`. A reviewed status/documentation change can retain evidence when its contract and execution inputs are unchanged. Filename alone supplies no exemption: changed specification/requirement objects, relevant source objects, workspace manifests/lockfiles, tooling configuration and scripts invalidate applicability regardless of a prose assessment. The exact primary owner’s canonical numbered issue has one narrow exception: an explicit `status-only` review may retain its requirement when the actual before/after Git blobs differ only in standalone `**Status:**` or `**Assignee:**` headers and their following blank separator. Status values must be recognized canonical states; each blob must contain exactly one Status header and at most one Assignee header. The CLI reads only those two public blobs, each bounded to 128 KiB, and compares every remaining byte. No prose/category exemption applies to acceptance text, other headers (including dependencies), other requirement files, duplicate/unknown metadata or unavailable blobs. Such changes still require renewed evidence or review. Changed toolchain, dependency, build, runner, fault, artifact or environment fingerprints also invalidate it. Any missing change assessment, unknown impact or changed input leaves `state: review-required`, never a pass. An explicit `unrelated` assessment of another source change requires semantic review of that exact edit and its affected scenarios.

A successful record reports `state: applicable` and evidence `freshness: carried-forward`. It counts only if every bound scenario has an applicable record. Original `failed`, `not-run` or `unavailable` observations cannot carry forward. Original artifacts must still be available. Human and JSON status retain the separate applicability records, reasons and reviewer; scenario `qualification` remains `not-assessed` because status is not a runtime observation.

Known stale evidence and incomplete resolved-ticket evidence in v3 produce ticket-scoped diagnostics and block affected consumers transitively. Unrelated eligible tickets remain in `frontier` while `complete: false` and exit 1 make the unresolved evidence visible. Current successful required verification and both reviews can supersede stale historical observations for eligibility. Missing roots, conflicting claims, an invalid dependency/allocation graph, malformed metadata or unverified integration mappings are integrity failures and withhold the entire frontier. Actual Git containment, coordinator receipts, ownership and the two-implementer bound still apply. Reconcile through the coordinator; status never changes canonical tickets or grants permission.
