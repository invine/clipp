# Read-only coordinator status

Start with [implementation, decisions and recovery](workflow.md). Clipp owns the ledger and CLI for both explicit repository roles; ticket `**Status:**` and `**Blocked by:**` fields remain authoritative. The command observes state and derives an eligible frontier. The coordinator saves claims before dispatch and reconciles diagnostics; the command never assigns work, releases claims, integrates, repairs or cleans up.

## Durable inputs

Keep the mutable run ledger and local configuration under ignored `.local/agent-workflow/`, outside disposable implementation worktrees. Save the ledger before dispatch and after each separate repository integration. A tracked ledger cannot record its own containing commit as the current tip: updating that hash creates another commit. Portable [run schema v1](ledger/run-v1.schema.json) and [example](ledger/run.example.json) stay tracked; [local schema v1](ledger/local-v1.schema.json) and [example](ledger/local.example.json) describe separately supplied roots and private artifact locations. Examples contain placeholders, not current status.

Keep current acceptance evidence in the ledger. Retain historical receipts separately in the artifact inventory; replacing current records does not alter those receipts. Source checks before integration remain source evidence and do not establish fresh integrated acceptance. A source branch or stash preserves work; neither proves integration. Renew current evidence after any integration revision changes, including documentation commits. Remove resolved claims explicitly when reconciling ownership; elapsed time never releases a claim.

## Invoke and interpret

From the selected Clipp checkout, with Node 22.22.1 or newer:

```sh
node scripts/agent-status.mjs --ledger .local/agent-workflow/run.json --local .local/agent-workflow/local.json
node scripts/agent-status.mjs --ledger .local/agent-workflow/run.json --local .local/agent-workflow/local.json --json
```

Both roots are mandatory and can select linked worktrees. Root selection must name a repository top level. Tracker/decision references use roles and relative paths; dependency links name numbered ticket files within the tracker. No sibling-path assumption is made. From the relay checkout invoke the same script by its selected Clipp absolute path, with explicit ledger/config paths.

Machine output has `schemaVersion: 1`, `observedAt`, `runId`, `complete`, repository HEAD/branch/integration tips, worktrees with dirty file counts, local `branches` (each with `branch`, `tip`, `integration` and associated `worktrees` paths), stash ref/commit IDs, tickets/dependencies/decisions/external blockers, claims with source branch containment, integrations, evidence freshness, active capacity, derived `frontier` and `{code, message}` diagnostics. Human output shows the same main facts. Dirty counts are file counts: a file staged and then edited counts in both staged and unstaged. Renames count once. Ignored artifacts are inventoried by explicit local references, not recursively searched. Submodule dirty state is outside this inventory.

`complete: true` and exit 0 mean required metadata is consistent, not that every ticket is resolved or acceptance passed. Pending decisions, external blockers, deferred tickets and existing claims are excluded from the frontier; unrelated eligible work can proceed within the two-agent capacity. Branch inventory includes unclaimed branches without worktrees. Branch `ancestry` means its tip is contained in the current integration tip; `verified-mapping` requires an explicit coordinator receipt mapping that exact source tip to a contained integrated commit. `unverified` means the branch preserves work without demonstrated integration; unrelated preserved branches are not assignment errors. Mapping a prior branch commit does not establish integration of a later tip. These states do not establish acceptance. Integration `ancestry` reports Git containment; `verified-mapping` reports a coordinator mapping with available receipt. `acceptance: pending` stays visible until checks and both reviews pass at the current revisions. Each ticket's role progress keeps partial cross-repository integration visible.

Exit 1 and `complete: false` mean reconcile actionable diagnostics before assignment; the entire frontier is withheld. This includes unavailable required roots/worktrees, malformed/cyclic/missing dependencies, ownership conflicts, changed recorded integration/source tips and stale/unavailable current evidence. Resolved tickets additionally require demonstrated integration for every role, all required successful verification profiles, fresh Standards and Spec reviews, and cleared blockers. Failed/not-run outcomes do not satisfy resolution. Native/live gates stay separate; a routine profile does not establish them.

The CLI reads only the explicit JSON metadata, bounded numbered Markdown tickets and Git metadata. It does not read source diffs, stash contents, runtime profiles, credentials, decision prose or artifact contents, and never executes ticket/evidence commands. Git optional locks and fsmonitor are disabled. Inputs are bounded to 1 MiB each, tickets to 128 KiB each, collections and local branch inventory to 500 entries and worktrees to 200; Git calls time out after 10 seconds, with an 8 MiB output limit. A report exceeding 1 MiB fails with `output-limit` rather than returning an incomplete frontier as success.

## Restart demonstration

Run the public Git-fixture acceptance suite:

```sh
npm test -- --runInBand tests/agents/agentStatus.test.ts
```

It creates temporary real repositories and linked worktrees, commits a ticket result before integration, restarts from durable JSON records, observes the outstanding source commit, retains an unrelated worktree with staged/unstaged/untracked files and a stash, and finds eligible work while another ticket is blocked and capacity ticket 33 is deferred. It compares all fixture Git refs, index and regular-file bytes before/after status. Other scenarios cover incomplete companion integration, cherry-picks, conflicting claims, missing/cyclic dependencies, decision evidence, stale or missing receipts, clean completion and inaccessible preserved worktrees. Synthetic private canaries never appear in output. The fixtures do not inspect the operator's private state.

For the current implementation effort, the coordinator saves the actual local ledger/config and dated status snapshot after integration and whole-effort review, and links their durable local locations from the canonical run record. That action does not change historical managed-relay backlog outcomes or deferred capacity ticket 33. Preserve existing worktrees and stashes until separately authorized cleanup.
