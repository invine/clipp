# Clip History

## Scope

This specification defines Clip identity, live Clip propagation, history exchange, retention, and duplicate suppression across Clipp's Desktop, Mobile, and Extension runtimes.

## Development migration scope

- Migration of legacy Clip and Clipboard History data is deferred until the 0.0.2 protocol-version work.
- During the current transition, implementations may delete legacy Clip/history data and initialize a clean history store.
- `/clipp/clip/1.0.0` does not negotiate or fall back to the legacy JSON `/clipboard/1.0.0` protocol.
- `/clipp/history/1.0.0` does not negotiate or fall back to the legacy JSON `/clipboard/history/1.0.0` protocol.
- The current scope requires neither legacy wire interoperability nor legacy data migration.

## Clip identity

- A Clip represents one clipboard capture event.
- A Clip's identity is event identity, not content identity.
- The Device Identity that first captures a Clip assigns its Clip ID exactly once.
- A Clip ID is a UUIDv4 generated by the originating device.
- A locally generated UUID becomes the Clip's assigned identity only when the initial atomic history insert succeeds; candidate UUIDs are never published first.
- If a candidate UUID conflicts with a different durable Clip or an unexpired suppression tombstone, Clipp generates another candidate and retries insertion up to three times without changing the capture's other immutable fields.
- If all three candidates conflict, Clipp abandons that capture: it creates no history record or pending item and sends no network message.
- Collision exhaustion writes a content-free diagnostic log; for an ordinary clipboard observation, the observer still advances its exact baseline so the unchanged value is not retried continuously.
- Protobuf represents the UUID as exactly 16 raw bytes in standard UUID byte order rather than as its 36-character text form.
- Local storage, logs, and debugging surfaces may render the same value as a canonical lowercase hyphenated UUID string.
- Decoders reject a Clip ID that is not exactly 16 bytes or does not have the UUIDv4 version and RFC variant bits.
- Every Clip carries the immutable canonical libp2p Peer ID of the Device Identity that originated its capture event.
- The origin assigns an immutable `capturedAt` timestamp encoded as protobuf `uint64 captured_at_unix_ms` in UTC milliseconds since the Unix epoch.
- Every forwarding and history hop preserves `capturedAt` unchanged.
- Clipboard History uses `capturedAt` for presentation ordering, but neither deduplication nor cross-device conflict resolution treats it as proof that one Clip is causally newer than another.
- Implementations validate the full 64-bit timestamp without first coercing it to an imprecise JavaScript `number`.
- The Clip's originating Peer ID is distinct from the immediate sender identity authenticated by the current libp2p connection.
- On the origin's first live transmission, the originating Peer ID equals the authenticated immediate sender Peer ID.
- A later forwarding or history hop preserves the originating Peer ID even though its authenticated immediate sender is another Active Member.
- Clips carry no application-level origin signature.
- A receiver accepts a Clip only from an immediate sender authenticated by the live libp2p connection and recognized as an Active Member.
- An Active Member that forwards or re-exports a Clip vouches for the complete Clip under its own authority; the forwarded `originPeerId` remains attribution metadata rather than portable proof of authorship.
- A Clip's `originPeerId` need not be Active or even present in the receiver's current Membership View when an authenticated Active Member forwards it.
- Revoking or losing the originating Device Identity does not invalidate an already held Clip or prevent another Active Member from offering it while its Clip Sharing Lifetime remains valid.
- Every live message, forwarding hop, persisted history record, and later history exchange preserves that original Clip ID unchanged.
- Receiving or applying a Remote Clip never mints a replacement Clip ID for that event.
- When an incoming Clip ID already exists, the receiver compares every immutable Clip field with the durable record.
- An exact match is an idempotent duplicate.
- If any immutable field differs, the first valid durably stored record wins and is never overwritten by the conflicting variant.
- A conflicting variant is not applied, forwarded, or exposed as another history entry; Clipp logs its Clip ID and authenticated immediate sender for debugging.
- A conflict affects only that Clip record and does not reject otherwise valid records in the same history batch.
- Two Clips may contain identical normalized content and still represent distinct capture events.
- Clipp never merges different Clip UUIDs based only on identical or similar content, nearby timestamps, or inferred user intent.
- Re-observing an unchanged clipboard through polling, restart recovery, transport retry, or remote-write echo must not create a duplicate Clip.
- Before Clipp writes a Remote Clip into the local system clipboard, it updates the local clipboard observer's baseline to that Clip's normalized content.
- Repeated observations of that unchanged remote-written value do not create a new Local Clip with a new UUID.
- On a polling runtime, Clipp serializes the observer with the Remote Clip write, silently reads the platform clipboard after a successful write, and replaces the observer baseline with the actual value returned by the platform.
- The read-back creates no Clip, does not alter the durable Remote Clip, and exists only to absorb platform transformations such as line-ending conversion.
- If the Remote Clip write succeeds but immediate read-back fails, the observer enters a local `baseline pending` state and retries read-back promptly.
- While the baseline remains pending, the first later successful clipboard observation establishes the exact baseline without creating a Local Clip; normal change capture resumes only afterward.
- This rule deliberately prefers preventing a transformed remote-write duplicate even though a genuine user copy during the unresolved interval may be absorbed as the baseline.
- A runtime that cannot read the clipboard in the background uses the intended Remote Clip content as its observer baseline.
- Clipboard-change and echo detection compare the exact observed text value with the current baseline rather than using the existing 32-bit custom hash.
- The observer retains only the current baseline value in memory; it does not persist or exchange that value as a separate record.
- An observed empty clipboard updates the local baseline but creates no Clip and sends no network message.
- Copying earlier non-empty content after that intervening empty value creates a new Local Clip event.
- When the system clipboard later changes to different normalized content, ordinary local capture resumes; deliberately returning to the earlier content after that intervening value creates a new Local Clip.
- On runtime startup, Clipp baselines the existing system clipboard without capturing it as a new Clip.

## Clip content

- `/clipp/clip/1.0.0` and `/clipp/history/1.0.0` support only UTF-8 text and HTTP(S) URL Clips.
- Image and file Clips are not valid in these v1 protocols and are deferred until a later protocol version with end-to-end runtime support and binary-transfer limits.
- The protobuf `Clip` message fixes `bytes clip_id = 1`, `bytes origin_peer_id = 2`, `uint64 captured_at_unix_ms = 3`, and `uint64 share_expires_at_unix_ms = 4`.
- `origin_peer_id` contains canonical libp2p Peer ID multihash bytes rather than a textual Peer ID; empty, invalid, and noncanonical encodings are rejected.
- Immutable equality compares those canonical Peer ID bytes.
- Its `oneof content` fixes `string text = 5` and `string url = 6`; there is no separate content-type enum or generic content field.
- The protobuf `LiveClip` message fixes `Clip clip = 1`.
- Future schemas reserve the number and name of every removed field and never reuse either for a different meaning.
- Missing content or protobuf input that sets both recognized content alternatives makes the Clip invalid.
- `text` must contain valid UTF-8 text after Clipp's text normalization; `url` must contain a valid absolute HTTP or HTTPS URL.
- Only the originating device normalizes and classifies clipboard content when it creates the Clip.
- Every receiver and forwarder validates the selected content alternative but preserves its encoded UTF-8 content byte-for-byte; it does not trim, rewrite, canonicalize, or reclassify the Clip.
- Immutable-field comparison and remote-write echo suppression operate on that preserved content.
- Origin normalization for a `text` Clip preserves the platform clipboard text exactly, including leading and trailing whitespace, tabs, line breaks, and control characters.
- A `text` Clip must be non-empty and encode as well-formed UTF-8; Clipp does not otherwise sanitize its content.
- User interfaces safely render or escape control characters without modifying the stored Clip.
- Origin classification selects `url` only when the entire untrimmed clipboard value parses as an absolute URL whose scheme is HTTP or HTTPS.
- A `url` Clip preserves the exact original clipboard string; Clipp validates with a URL parser but never stores the parser's canonicalized output.
- A URL surrounded by whitespace is a `text` Clip because classifying it as `url` would require changing the captured content.
- A locally captured Clip whose encoded live message cannot fit within the configured frame maximum remains a valid local Clipboard History record but is ineligible for either Clip protocol.
- The runtime logs the Clip ID and encoded size when excluding an oversized local Clip; it does not expose the Clip's content in the log.
- An oversized Clip never blocks propagation or reconciliation of smaller valid Clips.
- If a user copies content, then copies a different value, then deliberately copies the original content again, the final copy is a new Clip and remains separately visible in Clipboard History.

## Historical import

- A Clip is Local when its immutable `originPeerId` equals the current Device Identity's Peer ID and Remote otherwise.
- History storage does not persist or exchange a separate mutable `isLocal` classification.
- Clipboard History displays the Clip's immutable `originPeerId` as its source, resolved through Local Device Alias, latest known Device Name, then shortened Peer ID.
- The immediate peer that forwarded or re-exported the Clip is transport/debug metadata only and never replaces the displayed origin.
- A device may offer both Local Clips and Remote Clips from its Clipboard History to other Active Members during history reconciliation.
- A Clip therefore remains recoverable through another Active Member when its originating device is offline or no longer available.
- Re-export preserves the Clip's original ID and does not turn a Remote Clip into a Local Clip.
- Importing a historical Clip stores it in Clipboard History but does not apply it to the receiving device's current system clipboard.
- A Clip first learned through history reconciliation does not enter the live forwarding path, does not overwrite the current system clipboard, and does not produce a live-Clip notification.
- Once stored, an imported unexpired Clip may propagate further only through ordinary history reconciliation.
- A device records local durable metadata indicating whether it has handled a Clip through the live protocol; this metadata is not part of the Clip and is never exchanged.
- A newly stored Local Clip sets `liveHandled` true because the originating system clipboard already contains that capture event.
- If the Local Clip later returns through a gossip loop, its existing `liveHandled` state prevents the loopback from overwriting a newer clipboard value.
- Importing a Clip through history reconciliation does not mark it as handled live.
- If the same Clip ID later arrives through the live protocol for the first time, the device applies it to the system clipboard once even though the history record already exists.
- That live arrival creates no second history entry and does not repeat first-reception forwarding that was already made ineligible by the earlier historical reception.
- Further live deliveries of the same Clip ID do not apply it again.
- Each Clip has a finite Clip Sharing Lifetime.
- The originating Device Identity assigns an absolute `shareExpiresAt` timestamp when it creates the Clip.
- The origin computes `shareExpiresAt` from a device-level Clip Sharing Lifetime setting in effect at capture time.
- The production default Clip Sharing Lifetime is 24 hours.
- Every Clip Sharing Lifetime is finite; the device setting does not offer a `never expires` value.
- The production maximum Clip Sharing Lifetime is 30 days, measured as `shareExpiresAt - capturedAt`.
- Origins must not create and receivers must reject a Clip whose Sharing Lifetime exceeds that maximum.
- The maximum is deployment-configurable and injectable for tests, but is not an end-user setting.
- The setting applies automatically to every newly captured Clip and requires no per-Clip prompt.
- Changing the device-level setting affects only future Clips and never rewrites an existing Clip's `shareExpiresAt`.
- `shareExpiresAt` is immutable and is preserved unchanged in every live message, forwarding hop, persisted history record, and history exchange.
- A valid Clip requires `shareExpiresAt` to be strictly greater than `capturedAt`; zero, equal, or earlier values make the Clip structurally invalid rather than merely expired.
- Receiving, importing, or forwarding a Clip never restarts or extends its Clip Sharing Lifetime.
- While that lifetime remains valid, any Active Member holding the Clip may offer it during history reconciliation.
- Clip time validation uses an injected `clockSkewAllowance` with a two-minute production default.
- Tests and deployments may override `clockSkewAllowance`; it is not an end-user setting.
- A Clip is not yet valid when `capturedAt > now + clockSkewAllowance`.
- A Clip is expired when `now >= shareExpiresAt + clockSkewAllowance`.
- Immediately before live sending, forwarding, or adding a Clip to a history batch, the sender applies that expiration check against its own local clock and excludes an expired Clip.
- After the sharing lifetime ends, a device retains its existing local history record but does not send or forward that Clip.
- A device that did not receive the Clip during its sharing lifetime does not acquire it later, so Clipboard Histories need not converge for expired Clips.
- A receiver applies the same clock-skew-aware expiration rule using its local clock and discards an expired Clip without storing, applying, notifying, or forwarding it.
- Receiver-side validation is independent of sender-side filtering and uses the receiver's local clock.
- Receiver-side expiration does not delete an existing local history record for the same Clip ID.

## Reconciliation trigger

- Clipboard History reconciliation runs whenever an authenticated connection between two Active Members is established or re-established.
- Reconciliation is not limited to Pairing; later connection and reconnection triggers require no new Admission event.
- If an already-connected authenticated peer transitions into Active membership through Pairing or Membership Reconciliation, Clipp immediately triggers the same full snapshot and History Request flow without waiting for a reconnect.
- Enabling Auto Sync immediately initiates full eligible-history reconciliation with currently connected Active Members rather than waiting for a reconnect.
- Both peers participate independently, so each can repair Clips the other missed while offline.
- Once per established connection, each peer independently opens one outbound `/clipp/history/1.0.0` stream to the other Active Member.
- Each outbound history stream is semantically one-way: its opener writes zero or more size-bounded History Batch frames sequentially and then closes the stream.
- End-of-stream marks completion of that peer's current eligible-history snapshot.
- The receiver sends no response or acknowledgment on a snapshot stream.
- A receiver permits at most one active inbound snapshot stream per authenticated immediate-sender Peer ID and resets additional concurrent snapshot streams from that same sender with a content-free `snapshot busy` log.
- Inbound snapshots from different Active Member Peer IDs may be processed concurrently; the per-sender snapshot gate does not impose a global one-stream limit.
- A separate one-frame History Request from a sender remains permitted while that sender's snapshot is active.
- Repeating reconciliation on later connections is safe because import is idempotent by immutable Clip ID.
- In the initial protocol, each peer sends its complete set of Clips whose Clip Sharing Lifetime has not expired.
- A sender orders the eligible snapshot by descending `capturedAt`, with ascending raw Clip UUID bytes as the deterministic tie-breaker.
- This ordering controls transfer priority only and does not establish causal ordering or resolve conflicts between distinct Clips.
- At snapshot start, the sender captures that ordered set as a stable in-memory list of Clip IDs; it does not hold a database transaction open while performing network I/O.
- Immediately before encoding each listed Clip, the sender reloads it and rechecks record existence, local suppression, expiration, frame-size eligibility, and Auto Sync.
- A Clip deleted, suppressed, expired, or otherwise made ineligible after snapshot start is skipped; a Clip stored after snapshot start is excluded from the current snapshot and is covered by the per-target pending follow-up.
- If an eligible listed Clip cannot be read from local storage, the sender logs that Clip ID and a stable storage-error reason without content, skips only that Clip, and continues sending the rest of the snapshot.
- That isolated outbound read failure does not set the pending-follow-up flag or trigger an automatic retry; a later ordinary reconciliation trigger is the next opportunity to send the omitted Clip.
- Complete history is divided into bounded batches rather than placed in one unbounded message.
- For each batch, the receiver inserts only Clip IDs absent from its durable Clipboard History.
- The initial protocol uses no Clip-ID inventory, digest, cursor, missing-range request, or per-batch acknowledgment.
- An interrupted or failed reconciliation is retried from the complete eligible set when the peers next establish a connection.
- The initial version does not retry a failed history stream while the same connection remains open.
- Incremental reconciliation and transfer optimization are deferred.

## History request

- A History Request uses `/clipp/history/1.0.0` on a separate short-lived stream containing exactly one length-prefixed `HistoryRequest` control frame and then closes.
- Every history request and snapshot stream has a progress-based idle timeout with a 30-second production default, reset whenever a complete frame is successfully read or written.
- The idle timeout is deployment-configurable and injectable for tests, but is not an end-user setting; there is no total-duration deadline for a stream that continues making progress.
- Timeout terminates the stream as a failure. Already committed inbound records remain, and recovery follows the ordinary next-connection, History Request, or other later-trigger path without an automatic same-connection retry.
- A History Request carries no Clip IDs, cursor, timestamps, or sender identity fields.
- An authenticated Active Member with Auto Sync enabled responds by opening its ordinary one-way full-snapshot stream to the requester.
- The response is a separate snapshot stream, not data or an acknowledgment written on the request stream.
- A recipient with Auto Sync disabled ignores the request and sends no response.
- A snapshot never triggers another History Request, preventing request loops.
- When Auto Sync is enabled, the device opens its own outbound snapshots and sends one History Request to every currently connected Active Member so both directions reconcile without reconnecting.
- At most one outbound history snapshot may be in flight per target Peer ID, regardless of whether a connection event, Auto Sync enablement, or History Request triggered it.
- Additional triggers for that target coalesce while its snapshot remains in flight and do not start parallel duplicate transfers.
- The first such concurrent trigger sets one in-memory pending-follow-up flag for the target; any further concurrent triggers collapse into that same flag.
- After the in-flight snapshot reaches successful EOF, a set pending-follow-up flag starts exactly one fresh full snapshot so Clips stored during the earlier transfer do not have to wait for reconnection.
- If the in-flight snapshot fails, Clipp clears its pending-follow-up flag and preserves the existing no-same-connection-retry rule; the next connection, History Request, or other later trigger starts a fresh snapshot.
- Coalescing state is in memory only and has no cooldown.

## Auto Sync eligibility

- Auto Sync defaults to enabled on a new installation.
- Auto Sync is a persisted identity-independent installation preference that survives runtime restarts and Identity Rotation.
- The device-level Clip Sharing Lifetime and local-retention settings are likewise identity-independent installation preferences.
- Disabling Auto Sync does not add a permanent local-only flag to Clips captured while it is disabled.
- Local capture continues to assign the ordinary immutable `capturedAt` and `shareExpiresAt` and stores the Clip in local history.
- While Auto Sync is disabled, Clipp does not send those Local Clips through live propagation or outbound history reconciliation.
- While Auto Sync is disabled, Clipp ignores inbound live Clips and History Batch frames without storing, applying, notifying, or forwarding their records.
- Disabling Auto Sync cancels every in-progress outbound history snapshot immediately, abandons its unsent batches, and clears any per-target pending-follow-up flag; Clips already transmitted are not retracted.
- Re-enabling Auto Sync starts fresh full reconciliation rather than resuming a canceled snapshot.
- Disabling Auto Sync does not stop Pairing, Membership Reconciliation, revocation, reachability, or other non-Clip networking.
- Receive paths recheck Auto Sync immediately before durable Clip acceptance, so disabling it cancels an in-flight Clip that has not yet committed.
- Before starting queued clipboard application, notification, or forwarding for a committed live Clip, Clipp rechecks Auto Sync.
- If Auto Sync was disabled after commit, the history record and its `liveHandled = true` state remain, but every not-yet-started Clip side effect is canceled and later duplicates do not revive it.
- After Auto Sync is enabled, every Clip currently retained in local history becomes eligible for outbound reconciliation regardless of whether it was captured while Auto Sync was disabled.
- Expiration, frame-size eligibility, and local deletion tombstones still exclude a Clip; enabling Auto Sync never overrides them.
- Still-unexpired Clips missed while Auto Sync was disabled may return through the immediate history reconciliation, which stores them without overwriting the current system clipboard.
- Enabling Auto Sync does not replay the newest retained Clip through the live protocol.
- Only a later local capture or explicit history reuse creates a live update after re-enable; the retained backlog is history-only.

## History batch validation

- The receiver validates each Clip in a successfully decoded History Batch independently.
- Immediately before each Clip's atomic storage operation, the receiver rechecks that the authenticated immediate sender is still an Active Member.
- If the sender was revoked before that check, the Clip is discarded; a Clip already committed while the sender was Active remains valid and is not rolled back by a later revocation.
- A malformed, expired, locally suppressed, conflicting, or already-known Clip does not prevent other valid records in the batch from being imported.
- A malformed Clip is rejected and logged with a stable reason code, its Clip ID when safely decodable, and the authenticated immediate sender; logs never include Clip content.
- An exact duplicate is idempotent and need not produce a warning log.
- Invalid length framing, protobuf frame decoding failure, or a frame exceeding the configured maximum terminates that history stream.
- A local storage error while accepting an otherwise valid Clip also terminates the history stream, retains records committed earlier in the stream, and exposes the local storage error.
- Clipp does not continue consuming later frames after local storage becomes unavailable; a later connection or History Request retries from a full snapshot.
- Records imported from earlier valid frames or earlier valid entries are not rolled back when a later frame or record fails.
- The receiver tracks whether an inbound history stream durably imported at least one previously unknown, still-eligible Clip.
- When that inbound stream reaches EOF or terminates after importing new data, the receiver triggers ordinary full history snapshots to its other connected Active Members, excluding the immediate sender.
- A stream containing only duplicates, conflicts, expired Clips, malformed Clips, or locally suppressed Clips triggers no propagation.
- Propagated historical Clips remain history-only and never enter the live application or live forwarding path.
- Per-target in-flight coalescing applies to these triggered snapshots.
- This simple rule can create a wave of full-history messages across a partially connected Device Network; inventory exchange, deltas, debouncing, topology selection, and other wave optimizations are explicitly deferred.

## Invalid live messages

- An invalid live Clip receives no application-level error response.
- Clipp closes the invalid `/clipp/clip/1.0.0` stream but keeps the authenticated Active Member's underlying connection available for other protocols.
- A live-stream idle timeout follows that same stream-only close behavior and structured rejection logging.
- Clipp writes a privacy-limited structured rejection log containing a stable reason code, the authenticated immediate sender, and the Clip ID when safely decodable; it never logs Clip content.
- Unknown and revoked peers are not authorized to open either Clip protocol.

## Local deletion

- The initial Delete action removes a Clip only from the current device's Clipboard History.
- Local deletion does not send a deletion message and does not remove the Clip from any other device.
- Deleting an unexpired Clip creates a lightweight local suppression tombstone keyed by Clip ID and retained until `shareExpiresAt + clockSkewAllowance`.
- Removing an unexpired history record and creating its suppression tombstone are one atomic storage transaction.
- If local deletion persistence fails, the history record remains visible, no partial tombstone state is exposed, and Clipp presents a retryable error.
- While the tombstone exists, history reconciliation does not re-import the deleted Clip and live propagation does not restore, apply, notify, or forward it.
- Before starting any queued clipboard application, notification, or forwarding side effect for an accepted live Clip, Clipp rechecks that the record still exists and is not locally suppressed.
- A manual deletion, Clear History operation, retention cleanup, or capacity eviction that commits before such a side effect begins cancels that pending side effect; work already started cannot be retracted.
- The Clip's committed `liveHandled` transition is not rolled back, so a later duplicate cannot resurrect the canceled side effect.
- The device discards the suppression tombstone after `shareExpiresAt + clockSkewAllowance`, when receivers can no longer accept that Clip.
- Suppression tombstones have a separate production capacity limit of 100,000 records or 16 MiB of encoded tombstone data, whichever limit is reached first.
- Tombstone limits are deployment-configurable and injectable for tests, but are not end-user settings.
- Before evaluating that capacity, Clipp removes tombstones whose suppression deadline has passed.
- Clipp never evicts an unexpired tombstone to make room for another one.
- An inbound operation that would require a new tombstone beyond either limit is rejected atomically, leaves existing history and tombstones unchanged, and is logged without Clip content.
- A user Delete or Clear History operation that would exceed either tombstone limit fails atomically and exposes a visible, retryable capacity error.
- Automatic retention or capacity cleanup that cannot create all required tombstones leaves the affected history records intact and retries later.
- Clear History performs the same operation as locally deleting every retained Clip.
- Clear History creates suppression tombstones for removed Clips that remain acceptable during their skew-aware sharing window and creates none after that window closes.
- Clear History also discards every in-memory pending Local Clip that has not yet been durably stored.
- Discarding a pending Clip creates no suppression tombstone because the Clip was never shared or present in durable history.
- Clear History atomically removes its durable records and creates all required suppression tombstones before discarding pending captures.
- If that durable transaction fails, Clipp leaves both durable history and the pending-capture queue unchanged and presents a retryable error.
- Network-wide Clip deletion and replicated deletion tombstones are deferred for later reconsideration.

## Identity lifecycle

- Identity Rotation and Identity Loss cleanup delete the current installation's entire Clipboard History, including Local Clips, Remote Clips, pins, suppression tombstones, `firstStoredAt`, `liveHandled`, hop diagnostics, and pending local captures.
- No Clip or history metadata crosses from the former Device Identity into the replacement identity's singleton Device Network.
- The replacement runtime baselines the current platform clipboard without capturing it as a new Clip.
- Identity-independent Auto Sync, Clip Sharing Lifetime, local-retention, and frame-limit configuration survive rotation as previously specified.
- Other Active Members may retain valid Clips attributed to the former Peer ID; their copies are not remotely deleted by the origin installation's rotation.

## Pinning

- Pinning is local device state and is not part of the Clip exchanged on either protocol.
- A local pin prevents that device's ordinary retention cleanup from removing the Clip and keeps it available through the pinned view.
- Pinning never changes or extends the Clip's immutable `shareExpiresAt`.
- A pin is not propagated to other Active Members.
- After the Clip Sharing Lifetime ends, a pinned Clip remains only on devices that already retained and independently pinned it.

## Local retention

- Local history retention is a device-level setting independent of the Clip Sharing Lifetime.
- The production default local retention period for unpinned Clips is 30 days.
- The production maximum local retention period for unpinned Clips is one year; the setting offers no `forever` value.
- The retention maximum is deployment-configurable and injectable for tests, but is not an end-user setting.
- Local history also limits unpinned storage to 10,000 Clips or 100 MiB of encoded Clip data, whichever bound is reached first.
- Capacity limits are deployment-configurable and injectable for tests, but are not end-user settings.
- A single locally observed Clip whose encoded record exceeds the entire unpinned byte-capacity limit is not added to Clipboard History or the pending-capture queue and cannot be shared.
- Clipp still updates the observer baseline for that platform clipboard value, exposes a non-content-bearing `clipboard item too large` error, and does not retry the unchanged value on every observation.
- Clip Sharing Lifetime controls whether a Clip may cross the network; local retention controls how long an unpinned Clip remains in the current device's Clipboard History.
- The retention period starts when the current device first durably stores the Clip, not at the Clip's origin capture time.
- Each history record therefore keeps a local `firstStoredAt` value that is not part of the Clip and is never exchanged.
- `firstStoredAt` is assigned only by the first successful durable insert and never changes for that history record.
- Exact duplicate delivery, history reconciliation, first-live handling after historical import, and forwarding do not refresh local retention.
- The immutable origin capture time remains the Clip's presentation timestamp for history ordering.
- Local retention state and configuration are never propagated and do not mutate the Clip or its `shareExpiresAt`.
- Changing local retention applies immediately to every existing unpinned record using its unchanged `firstStoredAt`.
- Decreasing retention runs cleanup immediately; increasing it extends only records still present and never restores records already removed.
- Pinned Clips are exempt from ordinary local retention cleanup.
- Pinning is the only initial mechanism for retaining a selected Clip indefinitely, until it is unpinned or deleted.
- Unpinning immediately reapplies the current local-retention and unpinned-capacity policies.
- If the record's retention deadline has already passed, unpinning removes it immediately and atomically creates a suppression tombstone when its Clip Sharing Lifetime is still valid.
- If retention cleanup removes an unpinned Clip before its skew-aware sharing window closes, the device creates the same local suppression tombstone used for manual deletion.
- The retention-cleanup tombstone prevents live or historical restoration and expires at `shareExpiresAt + clockSkewAllowance`.
- Removal and any required retention-cleanup tombstone commit atomically; on storage failure, the history record remains and cleanup may retry later.
- When unpinned history exceeds a capacity bound, Clipp evicts the unpinned records with the oldest `capturedAt`, using raw Clip UUID bytes as the deterministic tie-breaker.
- Capacity ranking is distinct from retention timing: `capturedAt` selects the newest available event history under a storage shortage, while `firstStoredAt` still determines each retained record's local retention deadline.
- Capacity eviction atomically removes each still-shareable record with its local suppression tombstone and leaves pinned records exempt.
- A valid new Local capture or newly received live Clip has real-time admission priority: subject to item-size and tombstone limits, Clipp retains it and evicts the lowest-ranked existing unpinned records required to make room.
- A historical import has no such admission priority. Applying capacity selection to the combined candidate and existing unpinned records commits as one storage transaction, so the newest capacity-ranked set is retained.
- If a historical import is itself outside that retained set, the transaction does not expose a history record and creates a local capacity-suppression tombstone retained through `shareExpiresAt + clockSkewAllowance`.
- That outcome is reported as locally suppressed, triggers no live or historical side effect, and is not reconsidered merely because capacity becomes available or the Clip later arrives live during the same sharing window.
- All unexpired suppression tombstones are authoritative by Clip ID; the initial model defines no reason-specific override behavior.
- Capacity-eviction storage failure leaves the affected record intact, exposes a retryable storage error, and may retry cleanup later.

## Atomic duplicate suppression

- History storage performs tombstone lookup, Clip-ID lookup, immutable-field comparison, and insert-if-absent as one atomic operation.
- The operation reports exactly one outcome: newly stored, exact duplicate, immutable-field conflict, or locally suppressed.
- Live propagation and history reconciliation do not implement duplicate suppression as a separate check-then-insert sequence.
- The same transaction can atomically transition a matching record's local `liveHandled` marker from false to true and reports whether that transition occurred.
- Only a newly stored result may trigger newly-learned forwarding; an exact record imported through history may still produce its one `liveHandled` transition when the first live message later arrives.
- Exact duplicates with `liveHandled` already true, conflicts, and locally suppressed records never create another history entry or first-reception side effect.

## Persistence ordering

- A newly captured Local Clip is durably stored before Clipp attempts its first live broadcast.
- If that initial persistence fails, Clipp retains the same immutable Clip and UUID in an in-memory pending-capture queue and retries persistence with capped backoff while the runtime remains active.
- A new Local Clip that cannot commit because admitting it would require an unavailable tombstone slot enters that same pending-capture path rather than being discarded or partially stored.
- A retry after a non-conflict persistence or capacity failure never generates a replacement UUID or changes `capturedAt` or `shareExpiresAt`.
- Once an ordinary local observation has produced a pending capture, the observer immediately advances its exact baseline to the observed content even though durable insertion has not succeeded.
- Repeated unchanged observations therefore do not mint additional pending Clips; the queued capture remains the sole representation of that event.
- Clipp exposes a visible storage error while any local capture remains pending.
- Later local clipboard changes continue creating independent capture events while earlier captures await persistence.
- The production pending-capture queue is bounded to 100 Clips or 10 MiB of encoded Clip data, whichever limit is reached first.
- Pending-capture limits are deployment-configurable and injectable for tests, but are not end-user settings.
- If one pending candidate exceeds the pending queue's entire byte limit, Clipp discards that candidate without evicting any existing queued Clip, advances the ordinary observer baseline, and exposes and logs a content-free `pending item too large` error.
- Such a candidate creates no tombstone because it was never durably stored or shared.
- When adding a capture would exceed either bound, Clipp evicts the oldest pending captures until the new capture fits.
- Eviction preserves the visible storage error and logs only each discarded Clip ID and encoded size, never its content.
- An evicted pending Clip creates no deletion tombstone because it was never durably stored or shared.
- Pending local captures are not broadcast or offered through history reconciliation before they are durably stored.
- Persistence retries preserve original capture order for history presentation, but one failing queue entry does not prevent independent persistence attempts for later entries.
- A pending Clip that expires before persistence recovery is still stored locally when possible but is never shared.
- When persistence recovers, Clipp triggers history reconciliation for every successfully stored recovered Clip that remains eligible under Auto Sync, expiration, size, and tombstone rules.
- Clipp sends at most one recovered Clip through live propagation: the newest successfully stored pending Clip whose exact content still matches the current system clipboard, provided the Clip remains unexpired and size-eligible and either Auto Sync is enabled or that capture retains its in-memory Share Now override.
- Older recovered Clips are never replayed as successive live clipboard updates.
- The visible storage error remains until no pending capture still requires persistence.
- The pending-capture queue exists only in memory and is lost when the runtime stops or restarts; Clipp introduces no secondary emergency persistence mechanism.
- After restart, the ordinary startup-baseline rule applies even if the current clipboard matches a capture lost from the former pending queue.
- An incoming live Clip completes its atomic insert-or-compare operation and any first `liveHandled` transition before Clipp applies, notifies, or forwards it.
- Historical import durably stores a newly accepted Clip with `liveHandled` false before processing the next record.
- If required history persistence fails, Clipp does not broadcast, apply, notify, or forward that Clip and logs the failure without Clip content.
- A later capture or delivery may retry after persistence failure because no durable deduplication or `liveHandled` state was committed.
- After `liveHandled` commits, applying the Clip to the system clipboard is an at-most-once attempt.
- If the system clipboard write fails, Clipp logs the failure without content, retains the Clip in history, and does not retry the write automatically.
- A later duplicate live delivery does not clear `liveHandled` or trigger another clipboard write; the user may manually reuse the retained history entry.
- System clipboard application and first-reception forwarding are independent post-commit side effects.
- Failure to apply a Clip locally does not suppress its forwarding to other connected Active Members.
- Failure to forward to one peer does not roll back local history or prevent attempts to other eligible peers.

## Concurrent live Clips

- A device serializes system-clipboard application of distinct accepted live Clips in local receive-processing order.
- Every distinct Clip that makes its first `liveHandled` transition gets at most one application attempt; Clipp does not collapse different UUIDs even when their content matches.
- `capturedAt` does not reorder live application across either the same or different origin devices.
- The last successfully applied Clip in the local processing order determines the resulting system clipboard value.

## Explicit history reuse

- When the user explicitly copies a Clipboard History entry back into the system clipboard, Clipp first serializes the observer and attempts the platform clipboard write.
- Only a successful platform write becomes a new Local Clip capture event; write failure creates no new Clip or network message, leaves the original entry unchanged, and exposes an error.
- The new Clip receives a new UUIDv4, the current local Device Identity as `originPeerId`, a new `capturedAt`, and a new `shareExpiresAt` derived from the current device setting.
- The reused Clip preserves the selected entry's exact content but does not mutate or replace the older Clip.
- Explicit history reuse follows ordinary Auto Sync behavior: when Auto Sync is disabled, the new Clip is retained locally but is not transmitted. `Share Now` is the only user action that overrides Auto Sync for a single new Clip.
- Clipp updates the observer baseline for the explicit write so the polling or manual capture path does not create a second Clip for the same reuse action.
- Automatic application of a Remote Clip is not explicit history reuse and never creates a new Local Clip.
- An explicit Share Now action likewise creates a new Local Clip event even when the current clipboard exactly matches the observer baseline.
- Each Share Now invocation receives a fresh UUID and remains a distinct Clipboard History entry; repeated invocations are intentional events rather than duplicates.
- Share Now attempts the new Clip's initial live broadcast even when Auto Sync is disabled.
- This one-Clip outbound override does not enable Auto Sync, initiate history reconciliation, send older history, or change future capture behavior.
- Share Now does not bypass expiration, frame-size, Active Member, or persistence-before-broadcast requirements.
- If Share Now enters the pending-capture queue, its one-Clip override is retained only as in-memory queue metadata and is lost on restart.
- After persistence recovery, that override may send the Clip live with Auto Sync disabled only when it is the newest recovered Clip and its exact content still matches the current system clipboard.
- Older delayed Share Now events remain local and are not replayed as stale live overwrites.

## Capture coordination

- Every runtime routes polling observations, Android clipboard capture, Extension popup input, explicit history reuse, and any Share Now action through one shared capture coordinator.
- The capture coordinator is the sole authority that classifies content, allocates the final UUID, assigns capture and sharing times, performs atomic history insertion, updates observer state, and initiates live propagation.
- Runtime entry points identify whether input is an ordinary clipboard observation or an explicit user event, but never independently mint, store, or broadcast a Clip.
- Ordinary unchanged observations are suppressed by the exact baseline; explicit events follow their separately defined new-event semantics.

## Live propagation

- Live Clip propagation uses `/clipp/clip/1.0.0`.
- Clipboard History reconciliation uses `/clipp/history/1.0.0`.
- Negotiation, transfer, and failure of the live and history protocols are independent: either protocol may remain usable when the other is unsupported or fails.
- A failure of either Clip protocol closes only its affected stream, does not disconnect the authenticated peer, and does not alter Device Membership or revocation state.
- Neither protocol negotiates or falls back to its legacy JSON predecessor.
- Both protocols use protobuf wire encoding.
- Their protobuf decoders ignore unknown fields while strictly validating every recognized field.
- A receiver stores and compares only the recognized v1 Clip model and re-encodes only those known fields when forwarding or reconciling; it does not preserve opaque unknown protobuf bytes.
- Immutable-field equality is semantic equality of all recognized immutable fields, not raw serialized-byte equality or protobuf field ordering.
- Unknown fields may extend optional metadata only; a field that affects identity, authorization, validation, or propagation behavior requires a new protocol version because an older hop may discard it.
- Breaking changes to Clip identity, authorization, or propagation semantics require a new negotiated protocol ID.
- Both protocols use the standard unsigned-varint length prefix produced by libp2p-compatible `it-length-prefixed` framing.
- A malformed or overflowing varint prefix terminates the stream, and the 256 KiB production maximum is enforced from the decoded length before allocating or decoding the protobuf frame.
- The frame limit is deployment-configurable and injectable for tests, but is not an end-user setting.
- A live Clip message occupies one frame.
- Each `/clipp/clip/1.0.0` stream carries exactly one live frame and then closes.
- Each live stream has the same progress-based 30-second production idle timeout used by history streams, with the same deployment/test configurability and no end-user setting.
- Multiple live frames, trailing data, an invalid length prefix, or an oversized frame make that live stream invalid.
- Each Clipboard History batch occupies one frame; senders pack batches by encoded byte size rather than by a fixed Clip count.
- No encoded frame may exceed the configured maximum.
- A live frame contains only a `LiveClip` protobuf message with one required `Clip clip` field.
- Every history frame contains one top-level `HistoryFrame` protobuf with `oneof body { HistoryBatch batch = 1; HistoryRequest request = 2; }`.
- `HistoryBatch` contains one non-empty `repeated Clip clips = 1` field; `HistoryRequest` is an empty nested message whose enclosing `request` field makes the frame non-empty.
- Snapshot streams permit only `batch` bodies, while request streams contain exactly one `request` body; a missing body or a body inconsistent with the stream's role is invalid.
- Empty live frames, a missing live Clip, and empty History Batch frames are invalid.
- Neither envelope carries payload `from`, `to`, `sentAt`, hop-count, or signature fields.
- The immediate sender comes exclusively from the authenticated libp2p connection; Clip origin, capture time, and sharing expiration come from the nested immutable Clip.
- The live protocol handles low-latency individual Clip events that may update the system clipboard.
- The history protocol handles bounded bulk reconciliation and never updates the system clipboard.
- The originating device sends a newly captured, unexpired Clip to its connected Active Members.
- When a device receives an unexpired Clip through live propagation for the first time, it forwards that Clip once to its other connected Active Members, excluding the immediate sender.
- First reception is determined by the immutable Clip ID against the device's durable Clipboard History, not merely by an in-memory seen set.
- A Clip already present in durable Clipboard History creates no second entry and is not forwarded again. It is applied or notified at most once through the separately defined first `liveHandled` transition when a history-imported Clip later arrives live.
- A runtime restart does not make an already stored Clip eligible for first-reception behavior again.
- Optimizing the initial live propagation topology or message count is deferred; correctness initially relies on stable Clip IDs and first-reception duplicate suppression.
- Initial live broadcast and each eligible first-reception forward are single best-effort attempts per connected Active Member.
- A failed live send creates no in-memory or durable retry job and is not retried automatically while the same connection remains open.
- Failures for different recipients are independent; one failed send does not stop attempts to other connected Active Members.
- Full history reconciliation on a later connection is the repair path for a missed live delivery.

## Deferred decisions

- Optimization of full-history reconciliation waves, inventories, batching, and topology.
- Network-wide deletion semantics, which are explicitly deferred beyond the initial local-deletion model.
