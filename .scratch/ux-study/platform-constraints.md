# Platform constraints for the Clipp UX study

Researched: 2026-10-07. Baseline: `a2e1a64cad05eadb7c567b48e3ec45ce7cd51e33`. This establishes assessment criteria, not observed Clipp defects. Product direction: shared styling and terminology, runtime-adapted layouts, simple defaults and compact daily use.

## Platform facts and their implications

| Surface                   | Verified constraint                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Study recommendation / inference                                                                                                                                                                                                                                                                         |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Chrome toolbar popup      | Chrome auto-sizes content within **25×25–800×600 pixels**. A popup closes when focus moves outside it; users cannot keep it open after clicking away. [Action API](https://developer.chrome.com/docs/extensions/reference/api/action#popup), [popup lifecycle](https://developer.chrome.com/docs/extensions/develop/ui/add-popup?hl=en).                                                                                                                                                                                                                                                                                         | Measure the actual popup, including scrolling and reopen behavior. Settings, authentication and multi-step work need interruption/recovery checks. A page opened as a normal tab does not prove popup usability.                                                                                         |
| Chrome options            | `options_page` opens a new tab; `options_ui` can instead embed options in extension management. Embedded sizing depends on content and can behave poorly with responsive content. [Options documentation](https://developer.chrome.com/docs/extensions/develop/ui/options-page).                                                                                                                                                                                                                                                                                                                                                 | Clipp declares full-tab options, so do not impose the popup height cap on options. Evaluate popup-to-options navigation and both narrow and wide tab viewports. [Clipp manifest](../../apps/extension/manifest.json).                                                                                    |
| Electron                  | `getBounds()` measures the window; `getContentBounds()` measures its client area. `useContentSize` defaults to false. Maximized, normal and fullscreen states are distinct; macOS fullscreen transitions are asynchronous. [BrowserWindow](https://www.electronjs.org/docs/latest/api/browser-window), [constructor options](https://www.electronjs.org/docs/latest/api/structures/base-window-options).                                                                                                                                                                                                                         | Capture content bounds and renderer viewport separately; wait for fullscreen transition events before measuring. Check restore behavior and large-window use of space independently of narrow-window overflow.                                                                                           |
| Android insets / keyboard | Targeting SDK 35+ enables edge-to-edge on Android 15+; controls can overlap system bars without inset handling. Android 16 disables the edge-to-edge opt-out for target 36 on Android 16, although that opt-out still works on Android 15. Keyboard visibility and IME insets are observable; Android recommends `adjustResize` for AndroidX backward compatibility. [Insets](https://developer.android.com/develop/ui/views/layout/edge-to-edge), [version caveat](https://developer.android.com/about/versions/16/behavior-changes-16#edge-to-edge), [IME](https://developer.android.com/develop/ui/views/layout/sw-keyboard). | Test focus, submit/cancel, validation and scrolling with the actual keyboard open. Check status bar, cutout, gesture area and three-button navigation. A manifest flag alone is not proof that the WebView handles keyboard space correctly.                                                             |
| Android adaptive layouts  | Layout should follow the app's available window, including split-screen, rather than physical screen size. Target-36 apps on Android 16 have large-screen orientation/resizability restrictions ignored by default, with documented exceptions and a temporary opt-out. [Adaptive sizing](https://developer.android.com/develop/adaptive-apps/guides/support-different-display-sizes), [Android 16 behavior](https://developer.android.com/about/versions/16/behavior-changes-16#adaptive-layouts).                                                                                                                              | Include compact portrait, short landscape and tablet/split-screen windows. Android's 600/840dp width breakpoints are useful sampling boundaries, not mandatory Clipp navigation patterns. [WindowSizeClass](https://developer.android.com/reference/kotlin/androidx/window/core/layout/WindowSizeClass). |
| Android text / targets    | Android 14+ supports nonlinear font scaling up to 200%; native `sp` text participates automatically. Android recommends touch targets of at least **48×48dp**, which may exceed the visible icon. [Font scaling](https://developer.android.com/about/versions/14/features#non-linear-font-scaling), [touch guidance](https://developer.android.com/guide/topics/ui/accessibility/views/apps-views).                                                                                                                                                                                                                              | Test system font and display size independently. Verify how Clipp's WebView text actually responds; do not assume CSS text inherits native `sp` behavior. Judge the hit area, not just icon dimensions.                                                                                                  |

Source anchors at this baseline: Electron is pinned to **43.4.0**, Chrome declares minimum **109**, and Android uses Capacitor **7.x**, min SDK **23**, target SDK **36**. These are configuration facts, not installed runtime versions. [Electron package](../../apps/electron/package.json), [Chrome manifest](../../apps/extension/manifest.json), [Android package](../../apps/android/package.json), [SDK configuration](../../apps/android/android/variables.gradle).

## Accessibility criteria

Use the following selected WCAG 2.2 criteria as the web UI assessment baseline. These are conformance criteria; the W3C Understanding pages explain them. Applying them to native shells requires the informative [WCAG2ICT guidance](https://www.w3.org/TR/wcag2ict-22/). This limited study cannot establish full WCAG conformance.

| Criterion                                                                                                                                                                 | Assessment rule                                                                                                                                                                                                                                                                                                                                          |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [1.4.10 Reflow, AA](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)                                                                                              | Vertically scrolling content must retain information/functionality at **320 CSS px width** without two-dimensional scrolling, except genuinely two-dimensional content. A 1280px viewport at 400% page zoom is the standard equivalent. This is not a demand for zero vertical scrolling.                                                                |
| [1.4.4 Resize Text, AA](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)                                                                                     | Text must enlarge up to **200%**, including intermediate steps, without lost content/functionality, except captions and images of text. At least one supported resizing mechanism must work.                                                                                                                                                             |
| [1.4.12 Text Spacing, AA](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)                                                                                  | User overrides of line height 1.5×, paragraph spacing 2×, letter spacing 0.12× and word spacing 0.16× font size must preserve content/functionality where supported by the language. These are override tolerances, not required default styling.                                                                                                        |
| [1.4.3 Contrast, AA](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)                                                                                   | Text normally needs **4.5:1**; large text needs **3:1** (18pt regular / 14pt bold). Inactive controls, decoration and logotypes have exceptions.                                                                                                                                                                                                         |
| [1.4.11 Non-text Contrast, AA](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)                                                                        | Visual information needed to identify controls, states and meaningful graphics needs **3:1** against adjacent colors, with inactive/native-appearance and essential-graphic exceptions.                                                                                                                                                                  |
| [2.1.1 Keyboard, A](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html), [2.4.7 Focus Visible, AA](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html) | Functionality must be keyboard-operable except inherently path-dependent input; keyboard users need visible focus. Exercise every menu, dialog, form and scrolling region.                                                                                                                                                                               |
| [2.4.11 Focus Not Obscured, AA](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)                                                              | Author-created content must not **entirely** hide the focused component. Recommend fully visible controls as a stronger UX goal; partial obscuration is not automatically this AA failure.                                                                                                                                                               |
| [2.5.8 Target Size, AA](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)                                                                             | Pointer targets need **24×24 CSS px**, or a valid exception. The spacing exception tests non-intersecting 24px-diameter circles centered on undersized targets against other targets/circles. Other exceptions cover equivalent controls, inline text, unmodified native controls and essential presentation. Android's 48dp recommendation is separate. |

## Measurement rules

1. Record revision, OS/runtime versions, surface, window state, input method and fixture for every capture. Record screen resolution, OS display scaling, screenshot dimensions, renderer `innerWidth/innerHeight`, root `clientWidth/clientHeight`, `devicePixelRatio`, and `visualViewport` width/height/scale/offset when available. CSS pixels are distinct from physical pixels; page zoom and visual/pinch zoom are different, and DPR accounts for page zoom. [CSSOM View, working draft](https://www.w3.org/TR/cssom-view-1/#zooming).
2. For Electron, also record window/content/normal bounds, display work area and `scaleFactor`, plus `webContents.getZoomFactor()`. Display bounds/work area use **DIP points**, not native pixels. Do not infer content space from a screenshot's pixel dimensions. [Display](https://www.electronjs.org/docs/latest/api/structures/display), [zoom API](https://www.electronjs.org/docs/latest/api/web-contents#contentsgetzoomfactor).
3. For Android, record window size in **dp**, logical density, font scale, display-size setting, system/IME insets and WebView version. Native dp is density-independent; sp also responds to font preferences. Neither is automatically interchangeable with CSS px. [Android units](https://developer.android.com/training/multiscreen/screendensities).
4. Label synthetic viewport results separately from native observations. Resizing, DPR emulation and injected text scaling are useful stress tests; they do not establish popup lifecycle, OS insets or native font-scaling behavior.

| Android phone        | App windows around **360×640dp**, **412×915dp**, rotated **640×360dp**, plus split-screen where supported.                                                                                                                              | Keyboard closed/open; font default/intermediate/200% on API 34+; default/larger display size; cutout; gesture/three-button navigation; Back and resume.                                            |
| Android large screen | Window widths around **600dp**, **840dp**, **1200dp**; portrait/landscape; split-screen.                                                                                                                                                | Resize across boundaries with unsaved input/dialog open; short-height layouts; default/large font. Include API 35 and 36 for edge-to-edge differences, plus an older supported API for comparison. |

Run empty, typical and dense fixtures: long device names, peer identities, addresses, errors, permission prompts, many peers/history entries and concurrent status messages. Compare action reachability, wrapping/truncation recovery, scroll depth, persistent chrome height and unnecessary empty space. Prioritize pairwise combinations plus smallest-window/large-text/keyboard cases; expand only where evidence exposes risk. These are study recommendations, not platform mandates.

No application or user profile was launched. Installed-version behavior, supported zoom paths, WebView scaling and actual clipping remain runtime questions. Official “latest” documentation can differ from the pinned or oldest supported versions; record versions before attributing a finding.
