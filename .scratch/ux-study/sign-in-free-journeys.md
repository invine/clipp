## Native Chrome QR import: hidden connection failure

The user completed the native macOS image picker for the fresh Electron device's generated QR. Chrome options displayed green “QR scanned” feedback, but the actual `pairDevice` callback returned `ok:false`: **“The connection gater denied all addresses in the dial request.”** No device, pending/waiting request, connection or public Pairing error appeared; Electron received no request. The QR's Signed Peer Record independently verified and contained six direct addresses (TCP, WebSocket and WebRTC Direct, including loopback). Parsing/signature validity does not establish browser dial eligibility.

This is additional native evidence for **C07**, not a new finding: image import succeeded and the subsequent connection failure was silently discarded. The normal browser connection policy was not weakened. Successful Chrome remote Pairing/approval and notification routes still need an eligible route; the authenticated test relay remains behind the deferred account journey. No claim is made that every direct route fails.

## Actual native notification failure; delivery still unverified

Each new incoming request invoked Electron's real `Notification.show()`. It emitted `failed`, with the native error **“The operation couldn’t be completed. (UNErrorDomain error 1.)”** in the later observed attempts. No `show` or `click` event was observed. The test did not reset OS permissions, change the operator's shared Electron notification setting or synthesize a notification click. The exact OS authorization/packaging cause is not established by this receipt.

Pending requests still reached the app and could be accepted/rejected, but the failed notification had no in-app recovery message and History offered no pending indication. This strengthens **E12** under real native notification failure. It **does not qualify notification delivery, native selection destination, a deliberate OS denial/regrant journey, or production packaged-app notification behavior**. See the `notificationEvents` in [the final Pairing state](live-journey-evidence/local-pairing/electron-approval-retry-complete.json).

Chrome's isolated profile reported extension notifications granted and its required clipboard permissions present. Navigator permissions separately reported clipboard-read `prompt` and clipboard-write `granted`. Those API-layer readings are not proof of OS access. Chrome never received a signed request, so notification delivery/selection was not exercised there.
